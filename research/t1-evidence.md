## 3. Acceptance criteria → evidence

- **Versioned, schema-validated bundle with room for later fragments** — pydantic v2
  contract (`pipeline/src/bytebrains_pipeline/bundle/models.py`, rationale in its
  docstring); `fragments` is a dict keyed by fragment name, so later fragments
  (yield panel, coefficients) slot in without a schema bump. Emitted
  `data/processed/bundle.json` re-validates on load and carries a sha256 checksum
  over its fragments. Raw source files checksummed in `sources`.
- **Ground truth reproduced** — all four ticket values pass exactly (see command
  output above); 2019 tourist arrivals verified on both source files.
- **Basis discipline** — five separately labelled series: `arrivals_tourist_2015_2023`
  (tourist basis, 2023 file), `arrivals_visitor_2019_2024`, `arrivals_tourist_2019_2024`,
  `arrivals_excursionist_2019_2024` (2024 file), `inbound_consumption_tourist_2015_2024`
  (Jad 1A totals, tourist basis). The contract rejects a series whose id does not embed
  its window; no series spans or merges the two windows.
- **Offline fixtures** — committed xlsx fixtures, same discipline as `tools/dosm-cli`
  (recorded raw samples, no network).
- **One command** — `pipeline/.venv/bin/tsa-pipeline` (documented in
  `pipeline/README.md`).

## 4. Notes / decisions

- pydantic models chosen over a standalone JSON Schema file: one source of truth,
  runtime validation at emission and reload, and `Bundle.model_json_schema()` can
  publish JSON Schema for the dashboard team on demand (see models.py docstring).
- Jad 1A is tourist-basis (overnight) inbound consumption; the all-visitor Jad 1
  total is intentionally not emitted in T1 (ticket specifies Jad 1A totals).
- Multi-block duplication (the `% contribution` block repeats `Jumlah/Total`) handled by
  reading the first `Jumlah/Total` row (values block) only; test pins this.
- Not committed to git per ticket instructions.
